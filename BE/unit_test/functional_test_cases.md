# Functional Test-Case Matrix

The cases below map the requested use cases to the current frontend workflow and backend API surface. `Access control` records the intended role boundary and whether the current backend route explicitly enforces it.

| ID | Use case | Preconditions | Test steps | Expected result | Access control |
|---|---|---|---|---|---|
| FT-01 | UC-1 Login | Existing customer or staff account | Submit valid credentials to `POST /auth/login`; repeat with an invalid password | Valid credentials return a bearer token and user profile; invalid credentials return `401` | Public endpoint; credential validation is enforced by the auth service |
| FT-02 | UC-2 Register Customer Account | Username and email are not already used | Submit valid customer data to `POST /customers/`; repeat with duplicate username/email | Account is created with a hashed password; duplicates return `400` | Public endpoint; customer registration is intentionally unauthenticated |
| FT-03 | UC-3 Browse Menu | Menu items exist | Request `GET /menu-items/`; request a valid item type; request an invalid/empty type | Available menu items are returned; valid type filtering works; missing results return `404` | Public endpoint; no staff/admin role required |
| FT-04 | UC-4 Manage Cart | Customer is viewing the menu | Add items, change quantities, remove an item, and inspect the cart in the frontend | Cart totals update correctly and invalid quantities cannot create an order | Cart is frontend state; backend authorization must be enforced when the order is created |
| FT-05 | UC-5 Place Dine-in Order | Customer, available table, and selected menu items exist | Create a dine-in order through the cart workflow; choose QR or cash; confirm QR payment when applicable | Order is created, table becomes occupied, and a completed QR payment moves the order into the kitchen flow | Customer ownership should be enforced; current order routes do not consistently attach `get_current_user` |
| FT-06 | UC-6 Place Shipping Order | Customer has a shipping address and selected items | Create a shipping order and complete QR payment | Order requires QR payment and moves to `pending_confirmation` after payment completion | Customer ownership should be enforced; shipping confirmation is manager-controlled by workflow, but route guards are not consistently attached |
| FT-07 | UC-7 Chef Manages Kitchen Orders | Active chef account and assigned/preparing order exist | Chef views assigned orders; changes order from `preparing` to `ready` | Valid transition succeeds; invalid state transitions return `400`; next staff assignment is attempted | Intended role: chef; current staff/order routes need explicit role dependencies for endpoint-level enforcement |
| FT-08 | UC-8 Waiter Monitors and Manages Active Orders | Active waiter account and ready dine-in order exist | Waiter views assigned orders; changes order to `served`; requests completion where applicable | Assigned order is visible; valid waiter transition succeeds; completion flow updates order state | Intended role: waiter; current staff/order routes need explicit role dependencies for endpoint-level enforcement |
| FT-09 | UC-9 Delivery Man Ships Orders | Active delivery staff account and ready shipping order exist | Delivery staff views assigned shipping orders; changes order through delivery states | Order transitions `ready` → `delivering` → `delivered`; invalid transitions are rejected | Intended role: delivery_man; current staff/order routes need explicit role dependencies for endpoint-level enforcement |
| FT-10 | UC-10 Manager Views Dashboard Analytics | Authenticated manager/admin account and payment data exist | Request payment summary for week, date range, quarter, and year | Correct totals and breakdowns are returned; invalid period parameters return `400` | Intended role: admin/manager; current analytics route should be protected with `require_admin` |
| ACL-01 | Backend access control: valid staff | JWT payload contains an accepted staff role | Call `require_staff` with the decoded payload | Staff access is accepted | Unit-tested in `test_access_control.py` |
| ACL-02 | Backend access control: reject customer from staff endpoints | JWT payload contains `regular_customer` | Call `require_staff` with the customer payload | `403 Staff only` is raised | Unit-tested in `test_access_control.py` |
| ACL-03 | Backend access control: valid admin | JWT payload contains `admin` | Call `require_admin` with the decoded payload | Admin access is accepted | Unit-tested in `test_access_control.py` |
| ACL-04 | Backend access control: reject non-admin | JWT payload contains `waiter` or `regular_customer` | Call `require_admin` with the non-admin payload | `403 Admin only` is raised | Unit-tested in `test_access_control.py` |
| ACL-05 | Backend access control: invalid JWT | Token is missing, expired, or signed with the wrong key | Decode through `get_current_user` | `401 Invalid token` is raised | Unit-tested in `test_access_control.py` |

## Current access-control gap

The role helper functions exist in `app/core/dependencies.py`, but most controller routes currently declare only `db: Session = Depends(get_db)`. The ACL cases above verify the helpers themselves; they do not claim that every staff or manager endpoint is already protected. The next hardening step is to attach `Depends(require_staff)` or `Depends(require_admin)` to the relevant route groups and add endpoint-level `TestClient` cases.
